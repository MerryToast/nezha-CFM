## [P2] 重新验证先于全量查询完成时，恢复请求被旧查询合并掉

位置：`src/context/cfsm-provider.tsx:422`、`:425`；后续状态更新在 `:506`，恢复 effect 在 `:640`。

`coveredByInFlight` 只要发现正在执行全量查询，就直接返回该查询的 Promise。这个判断未区分“该站已经成功查询”和“该站的旧凭证请求已经失败、正在等待其他站点返回”。因此，验证成功后的定向恢复也会被一个已经无法成功读取该站的旧查询吞掉。

生产构建浏览器复现步骤：

1. A/B 两站正常显示，凭证按站缓存。
2. B 凭证过期，页面从隐藏切回可见，开始查询 A/B 列表。
3. B 在 80ms 后返回 403；A 的列表响应延迟 800ms。
4. 完成 B 的重新验证，使其早于 A 的旧列表请求结束。
5. 验证后触发的 B 定向恢复遇到尚在进行的全量查询，被 `return current.promise` 合并。
6. A 返回后，旧查询仍以 B 失败处理：页面仅显示 A，B 留在 pending 集合；恢复 effect 的依赖已经在验证完成时变化过，不会因 pending ref 再次写入而执行。

实测结果：B 已成功取得新凭证，聚合 `verified=true`；但之后没有携带新凭证的 B `/api/servers` 请求，列表总数为 1，最终 WS 也只订阅 A。需要再次切回前台或刷新才能补齐 B。

建议局部修正现有合并分支：定向恢复等待进行中请求结束后，重新检查 pending 集合；若该站仍未成功同步，再执行一次恢复。已成功同步的站点直接复用结果，避免恢复第三轮的重复查询。无需新增轮询或通用重试框架。
