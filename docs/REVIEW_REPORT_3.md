# 第三轮审查报告

审查日期：2026-11-16。

第二轮列出的四个原始现象已不再出现：验证后节点能恢复，暂停后保存主题不会重连，详情能保留所属站点的显示开关，各后端也会按自己的时长超时。本轮确认仍有两项 P2 问题，均可在现有调用链内局部修正。

## 1. [P2] 验证恢复重复请求同一站点列表，并重复重建 WS

- 位置：`src/context/cfsm-provider.tsx:413`、`:593`、`:613`。
- 原因：首页在验证成功后重新挂载，`mountDashboard()` 对待补齐站点发起一次定向加载；Provider 的恢复 effect 又对相同站点发起一次。定向加载遇到进行中的请求时，只等待它完成，随后仍使用原 targetIndices 再查询一次，没有复用已覆盖同一站点的结果，也没有在等待后重新检查 pending 集合。
- 生产构建浏览器复现：A/B 两站正常载入，让 B 凭证过期并触发隐藏到可见。B 重新验证成功后，记录到两次携带新凭证的 `GET /api/servers`，两次都成功；B 的 WS 也建立、关闭、再次建立。A/B 节点最终均能显示，因此原来的“缺少 B 节点”已修复，但恢复仍产生多余查询和连接重建。
- 影响：每次验证恢复多消耗一次列表查询及其三网窗口查询，并短暂中断刚恢复的实时连接。
- 最小修正：统一恢复的触发入口，或让同站定向恢复复用已有请求。如果必须等待另一项加载，应在等待结束后重算仍需补齐的站点，再决定是否查询。

## 2. [P2] 第一站配置失败时，保存权限与实际保存目标不一致

- 位置：`src/api/cfsm-client.ts:335`、`:350`；`src/context/cfsm-provider.tsx:268`。
- 原因：`mergeSiteConfigs()` 使用“第一个配置请求成功的站点”作为 primary，并直接采用它的 authorization；保存主题选项却始终调用 `postThemeOptions(nextOpts, 0)`。当 index 0 配置未成功、index 1 成功时，显示的保存权限来自 B，实际写入目标仍是 A。
- 生产构建浏览器复现：A 的 `/api/config` 返回 503，B 的配置返回 `authorization:true`。页面使用 B 标题且聚合 authorization 为 true；执行已有保存操作后，请求实际发往 A 的 `/api/theme_options`。模拟 A 对该写操作返回 401 后，页面进入全局私密锁屏。
- 影响：部分后端配置不可用时，界面错误显示可保存，操作随后失败；即使 A 允许写入，也会出现展示配置来源和保存目标不一致。
- 最小修正：保存固定指向 index 0 时，保存权限必须取 index 0 的配置；不能用 B 的授权状态替代 A。保持配置来源、权限判断与写入目标一致即可。
