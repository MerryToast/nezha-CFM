# 第二轮审查报告

审查日期：2026-11-16。对应用户根据第一轮审查修改后的当前工作区。

结论：第一轮 9 项中，8 项的对应修正已通过代码核对和针对性验证；多后端首次验证、凭证隔离及普通权限判断也已修正，但后续恢复和配置使用仍有缺口。本轮保留 4 项能复现的功能问题，建议局部修改，不需要增加通用防御层、自动重试框架或 REST 轮询。

## 1. [P1] 多后端重新验证成功后，失败站点仍从列表和订阅中缺失

- 位置：`src/context/cfsm-provider.tsx:224`、`:378`、`:398`、`:471`、`:490`。
- 原因：后台切回前台时，`fetchServersAll()` 允许返回部分成功。B 因凭证过期返回 403，Provider 将仅含 A 的结果写回节点表，并将 `dashboardFetchedRef` 设为 true。B 验证成功后只更新 config，首页重新挂载时走“已加载”分支，仅按现有 A 节点重建 WS，没有补齐 B 列表。
- 浏览器复现：A/B 各一台节点，首次各用自己的凭证正常显示；让 B 凭证过期，触发一次隐藏到可见。观察到 B 的列表请求 403、随后 B 的 `/api/config` 验证成功；最终 `verified=true`，但列表总数从 2 变成 1，WS 也只订阅 A。B 没有再次查询 `/api/servers`。
- 影响：人机验证已经成功，页面却继续缺少站点及其实时数据，需额外刷新或再次切回前台才能补齐。
- 最小修正：记录这次鉴权失败对应的列表待补齐状态，验证成功后补齐受影响后端的列表再恢复订阅；不要把不完整列表视为该站已完成初始化。此请求是验证后的恢复，不是定时轮询。

## 2. [P2] 保存主题配置会重置详情页并绕过用户暂停选择

- 位置：`src/hooks/use-server-detail.ts:224`、`:240`、`:268`；触发源 `src/context/cfsm-provider.tsx:262`。
- 原因：详情初始化 effect 依赖整个 config；保存主题选项会创建新的 config 对象，从而清空历史、重设 10m、再次请求当前指标和历史，并无条件调用 `startSocket()`。`closedByUserRef` 只在可见性恢复入口被检查，初始化入口没有检查。
- 浏览器复现：管理员打开详情，站点超时设为 1 分钟；推进时钟触发弹窗，选择“保持静态展示”，再执行页面已有的主题保存操作。观察到新增 `/api/server`、`/api/history/all?...hours=0.167` 请求，WS 数量从 1 增到 2，新连接处于开启状态，未选择“继续实时连接”。
- 影响：主题外观保存产生无关历史查询，并恢复用户已明确暂停的数据流；原先选择的历史范围也会丢失。
- 最小修正：让节点初始化只随目标节点和必要的访问状态变化执行；主题配置变化继续走已有的内存重新归一化路径。自动连接入口同时尊重用户暂停状态。

## 3. [P2] 进入详情页后，已知的站点显示开关被默认值覆盖

- 位置：`src/api/cfsm-client.ts:624`、`:625`、`:636`；使用位置 `src/components/ServerDetailOverview.tsx:90`。
- 原因：首页已取得所属站点的 `sysConfig.show_tf=false`，但详情请求重新从 `DEFAULT_SYS_CONFIG` 构造开关，未复用该站已取得的 sysConfig。实际详情 API 的 sysConfig 只含 `long_history_points`，并不返回这些显示开关，所以默认 true 会保留下来。详情组件现优先使用这个新对象，覆盖了原本正确的全局缓存值。
- 浏览器复现：列表返回 `show_tf=false`，首页没有流量条；从该首页切到同一节点详情，详情 API 按文档只返回 `sysConfig:{long_history_points:120}`，页面又显示了月流量进度条。
- 相关残留：`src/components/PlanInfo.tsx:74`、`:80` 仍用全局 sysConfig 决定配额标签，未使用节点所属站点的开关；多站开关不同时标签与流量条可能不一致。
- 最小修正：按站缓存列表已返回的 sysConfig，详情缺少的字段从同站缓存合并，子组件也接收该站开关。无需额外请求 `/api/servers`。直达详情时接口没有提供的字段，应单独明确默认行为，不能把默认 true 当作已获取到的设置。

## 4. [P2] 多后端 WS 仍统一使用第一站的超时时长

- 位置：`src/context/cfsm-provider.tsx:318`、`:334`；详情同类位置 `src/hooks/use-server-detail.ts:185`。
- 原因：虽然已有 `getSiteConfigByIndex()` 和独立站点配置，创建各站 WS 时仍从聚合 config 读取 `frontend_ws_timeout_minutes`。聚合配置的该字段来自第一站。
- 浏览器复现：A 配置为 0 分钟（不限时）、B 配置为 1 分钟，打开聚合首页并推进 61 秒。两站 WS 都仍开启，没有超时弹窗，B 的 1 分钟策略未执行。
- 影响：第一站不限时或时长较大时，其他后端的连接额度限制失效；第一站时长较小时，又会过早暂停其他站点。
- 最小修正：创建 WS 时按 apiIndex 读取该后端的超时参数；单机详情也读取所属后端的配置，弹窗显示相同的时长。
